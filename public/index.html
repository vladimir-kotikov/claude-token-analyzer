Spend over time ?
Each API call's usage is split into 5 token types, stacked bottom (smallest, typically) to top:
input
Fresh, uncached prompt tokens sent this turn. Usually near-zero once a conversation is warmed up — most of the prompt is served from cache instead.
output
Tokens the model generated this turn, including extended-thinking/reasoning tokens (not just the visible reply text).
cache write (5m)
Prompt tokens newly written into the 5-minute ephemeral cache — billed higher than a cache read, cheaper than fresh input.
cache write (1h)
Same as above, but written to the 1-hour cache tier (costs more per token than the 5m tier, lasts longer).
cache read
Prompt tokens served from a previous cache write — the cheapest tier, but usually the largest volume since the whole growing conversation gets re-read every turn.
Daily = each day's own spend. Cumulative = running total, resets to 0 at the start of the selected month. USD/Tokens/Turns switches what's measured; Linear/Symlog switches the y-axis scale (symlog helps when cache read dwarfs the other series).

Sessions by health ?
Count of distinct sessions active each day, bucketed by that session's lifetime health tier (same badge as the session tables):
healthy
< $0.10/turn average.
elevated
$0.10–0.25/turn average.
high
>= $0.25/turn average — usually a long session running without compaction.
A session active across multiple days counts once per day it touched, always under its one overall tier. Daily only — no cumulative mode, since summing a repeating session's daily count wouldn't mean "total unique sessions".

Session detail ?
Each point is one assistant turn (one API call) in this session, in order — not a calendar day. Hover a point to see its timestamp and which tools it called. Uses the same USD/Tokens unit and Linear/Symlog scale as the chart above.

Tool output volume (bytes injected into context) ?
tool
name of the tool or MCP server called (e.g. Bash, Read, mcp__...).
calls
how many times this tool was invoked.
bytes
total size of that tool's results fed back into the model's context, across all calls.
est. tokens
bytes ÷ 2.18 — the API never reports per-tool-result token counts, so this is an estimate. The 2.18 bytes/token ratio was measured from this dataset (1,989 turns whose only new context was a single tool result, comparing its byte size to that turn's cache-write tokens); denser than the ~4 chars/token prose rule because tool output is code, JSON and logs.
avg tokens
est. tokens ÷ calls — a large average means each call injects a lot of context; candidates for trimming (tail/grep piping, ranged file reads, narrower MCP queries).

tool calls bytes est. tokens avg tokens

Top sessions ?
session
session ID — click the row to filter the whole page to just this session.
project
working directory the session ran in.
turns
number of assistant API calls in this session.
tokens
total tokens (all 5 types combined) across the session.
tokens/turn
tokens ÷ turns — the key diagnostic. High = each call re-reads a large/growing context, often one long-running session that never got compacted or restarted. Many turns with a low tokens/turn means the cost is volume (lots of cheap calls), not one bloated call.
days span
calendar days between the session's first and last turn. A session spanning many days is usually a resumed/background job whose context kept growing turn over turn.
$ input / $ cache write / $ cache read / $ output
cost breakdown by token type — see the chart's own "?" for what each means.
$ total
sum of the four cost columns above.
